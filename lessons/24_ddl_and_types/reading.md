# Reading - 24_ddl_and_types

Part 4 changes your seat at the table. For twenty-four lessons the schema
was a fact of nature; now you cause it. Every type you choose is a promise
enforced on every future write by every future application, in every
language, forever — which makes type selection the cheapest correctness
work available to you.

## Notes

**`text` versus `varchar(n)`.** In PostgreSQL these are the same type with
the same storage and the same performance; `varchar(n)` merely adds a length
check. That check sounds prudent and is usually a future outage: names,
addresses and identifiers are longer than you think in some locale, and
changing the limit later requires an `ALTER TABLE`. House style in most
PostgreSQL shops is `text`, with a `CHECK (length(x) <= n)` when a limit is
genuinely part of the domain. (`char(n)` is worse still — it pads with
spaces. Do not use it.)

**`numeric` versus `float` for money.** `numeric` is exact decimal
arithmetic; `double precision` is IEEE 754 binary, and 0.1 has no exact
binary representation. Ten dimes stored as floats do not add to one dollar —
you will watch this happen in ex2. `numeric(10,2)` means ten significant
digits with two after the point. The rule is absolute: money, quantities that
must reconcile, and anything a human will audit go in `numeric`. Floats are
for measurements and scientific work where relative error is acceptable and
speed matters.

**`timestamptz` versus `timestamp` versus `date`.** An instant that happened
gets `timestamptz`. A calendar concept — a birthday, a coupon's validity
date, an invoice period — gets `date`, because it is not a moment in time at
all. `timestamp` without a zone is almost never what you want; lesson 18
argues it fully.

**Booleans are a type.** `'Y'`/`'N'` text flags, `0`/`1` integers and
`'true'`/`'false'` strings all exist in legacy schemas and all permit values
that mean nothing. A `boolean` column has three possible states (true,
false, NULL) and if you add `NOT NULL` it has two, which is what you meant.

**Closed sets: CHECK versus enum.** PostgreSQL has real `enum` types, and
they are compact and ordered — but adding a value requires `ALTER TYPE`, and
until PostgreSQL 12 you could not do that inside a transaction, and you
still cannot *remove* one. The common house style is `text` with a `CHECK
(col IN (...))`: readable, changeable with an ordinary migration, and just
as enforced. The third option — a lookup table with a foreign key — is right
when the set is data (categories, countries) rather than code.

**Identity columns.** `GENERATED ALWAYS AS IDENTITY` is standard SQL and the
modern replacement for `serial`. Two practical advantages: `ALWAYS` rejects
explicit inserts, so nobody can hand-place an id that later collides with the
sequence; and the sequence's ownership is properly recorded, so it is dropped
with the table. Use `GENERATED BY DEFAULT AS IDENTITY` only when a data
loader genuinely needs to supply ids.

**Generated columns.** `GENERATED ALWAYS AS (expr) STORED` computes a value
from the same row's other columns and stores it. It cannot drift, because it
cannot be written. This is a *constraint* wearing a column's clothing:
anywhere your application maintains a derived field by hand, a generated
column removes the possibility of the two disagreeing. The limitation is
that the expression must be immutable and may only reference the current
row — no subqueries, no `now()`, no other tables.

**Arrays versus join tables.** PostgreSQL stores `text[]` happily, and it is
fine for a small, closed, order-insensitive list nobody joins against or
constrains. The moment you want "which products have tag X, guaranteed to be
a tag that exists", you want a join table with a foreign key. Arrays and
JSONB are the optimisation; normalisation is the default. Lesson 26 makes
the argument properly.

**Design for the constraint you cannot add later cheaply.** Every one of
these choices is easier now than after a billion rows exist. Lesson 28 is
about doing it afterwards anyway, safely, and it will make you appreciate
getting it right the first time.

## ex1 — the coupons table

Six columns, each a decision: `text` for the code, `numeric(5,2)` for a
percentage, `date` for calendar bounds, and one deliberately nullable column
so you can see the gate's probe insert omit it. Note `notes text` with no
`NOT NULL` — nullable *on purpose* is a legitimate design, and saying so
explicitly is what distinguishes it from nullable by accident.

## ex2 — watch float money break

The canonical schema-review catch, performed on your own table. Run `SELECT
sum(amount_float) FROM ledger` in the lab and look at the digits. Then
consider that this error compounds: every addition can introduce a new one,
and a ledger that has been summing floats for a year cannot be reconciled by
anyone. There is no rounding strategy that fixes it, because the wrong value
was stored, not merely displayed.

## ex3 — a table that refuses nonsense

Four type decisions plus a CHECK, and the gate proves each one bites.
Notice how much application code this table makes unnecessary: no plan
validation, no default-active logic, no "is this a date or a timestamp"
argument in code review. Every rule enforced here is enforced for the batch
script somebody runs at 2 a.m. too.

## ex4 — let the database do the arithmetic

Identity and generated columns are both answers to the same question: *what
can I stop trusting my application to get right?* A hand-maintained `total`
column is correct until the day someone updates `tax` through a code path
that forgot; a generated column is correct by construction. The gate's
rejection probe is the proof — there is literally no INSERT that can make
`total` disagree.

## Further reading

- [Data Types](https://www.postgresql.org/docs/16/datatype.html) — the whole chapter is worth a skim once; the numeric and date/time sections are worth reading properly.
- [`CREATE TABLE`](https://www.postgresql.org/docs/16/sql-createtable.html) — identity columns, generated columns, and the exact syntax for inline constraints.
