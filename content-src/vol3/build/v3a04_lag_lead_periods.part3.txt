## Exercise 6 — baselines and the last_value trap

Edit `ex6/solution.sql`.

Works against the same 44-row rollup as exercise 5: `orders` restricted to
`created_at >= '2023-01-01'`, grouped to (`month`, `status`).

Finance wants each status indexed against its own starting point: January =
100, and every later month expressed as a percentage of it. They also want
the status's final month on every row, for the footer of the chart.

`first_value` and `last_value` both read a row out of the **frame** — unlike
`lag` and `lead`, which ignore it. The default frame runs from the start of
the partition to the current row, so `first_value` is accidentally right and
`last_value` returns the current row's own revenue. Both columns need a
frame that spans the whole partition.

Illustration for one status:

```
   month    | status | revenue   | first_month | last_month | index_vs_first
------------+--------+-----------+-------------+------------+---------------
 2023-01-01 | paid   |21000000.00| 21000000.00 | 20400000.00|         100.00
 2023-02-01 | paid   |19500000.00| 21000000.00 | 20400000.00|          92.86
 2023-03-01 | paid   |22050000.00| 21000000.00 | 20400000.00|         105.00
 2023-11-01 | paid   |20400000.00| 21000000.00 | 20400000.00|          97.14
```

`first_month` and `last_month` are constant within a status. If your
`last_month` column equals `revenue` on every row, you have met the default
frame.

`first_month` (that status's earliest month's revenue), `last_month` (that

`lag` over a non-unique ordering returns one of the tied rows without
telling you which.

days passed. The most recent hire has no successor, so both of those columns
are NULL for exactly one row.

`lead` is `lag` pointing forwards: the NULL lands at the end of the series
instead of the beginning.

Illustration on four hires:

```
 id | hired_on   | next_hired_on | days_to_next
----+------------+---------------+-------------
  7 | 2015-03-02 | 2015-04-11    |           40
 12 | 2015-04-11 | 2016-11-30    |          599
  4 | 2016-11-30 | 2016-11-30    |            0
 31 | 2016-11-30 |               |
```

Rows three and four share a hire date, which is why the window's `ORDER BY`
needs `id` as a tie-break: without it, the order between them — and
therefore which one gets the NULL — is undefined.

Note that `date - date` in PostgreSQL yields an integer number of days
directly, with no `extract` and no cast required.

Columns, in this order: `id`, `name`, `hired_on`, `next_hired_on` (the next
finance hire's date, NULL for the most recent hire), `days_to_next`
(`next_hired_on - hired_on`, an integer, NULL for the most recent hire).

**Ordered by `hired_on` ascending, then `id` ascending.** (61 rows.)

## Hint 1

Same construction as the rest of the sector, pointed the other way. Nothing

## Hint 2

```sql
lead(hired_on) OVER (ORDER BY hired_on, id)
```

`lead(x)` is the value of `x` one row later in window order, or NULL if
there is no such row.

## Hint 3

Two `date` values subtract to an `integer` — days — so `days_to_next` needs
no `extract`, no division and no cast. That is a real difference from
exercise 7, where the operands were `timestamptz` and the result was an
`interval`. The decision left to you is whether to compute `lead` once in a
CTE or twice in one select list; both are correct, and only one of them lets
you name the intermediate value.

## Hint 1

Predict the NULLs first. Exactly one row — the most recently hired person in
finance — has NULL in both new columns. If you have more than one, check
whether you accidentally partitioned by something; if you have none, check
whether you used `lag` instead of `lead`.

## Hint 2

Look hard at the two people sharing a hire date in the illustration. The
first of them has `days_to_next = 0`, which is correct and looks like a bug.
Whether id 4 or id 31 gets the zero is decided entirely by the tie-break in
the window's `ORDER BY` — remove it and the answer becomes whatever the sort
happened to produce. Ties are where "it worked on my machine" comes from.

## Hint 3

Worth noticing on the way out: this same query, with `lag` instead of
`lead`, answers "how long since the previous hire" and puts the NULL at the
other end. The two reports are the same data read in opposite directions,
and choosing between them is a presentation decision rather than a technical
one — except for one thing, which sector v3a04's reading covers: `lead`
forces the executor to buffer rows it has not yet emitted, so on very large
partitions the backward-looking version is the cheaper of the two.
@@@FILE review1/solution.sql
-- v3a04_lag_lead_periods / review1 — the gap to the next finance hire.
WITH fin AS (
    SELECT id,
           name,
           hired_on,
           lead(hired_on) OVER (ORDER BY hired_on, id) AS next_hired_on
    FROM staff
    WHERE department = 'finance'
)
SELECT id,
       name,
       hired_on,
       next_hired_on,
       next_hired_on - hired_on AS days_to_next
FROM fin
ORDER BY hired_on, id;
@@@FILE review1/expected.sql
WITH fin AS (
    SELECT id, name, hired_on
    FROM staff
    WHERE department = 'finance'
),
paired AS (
    SELECT f.id,
           f.name,
           f.hired_on,
           (SELECT min(n.hired_on)
              FROM fin n
             WHERE (n.hired_on, n.id) > (f.hired_on, f.id)) AS next_hired_on
    FROM fin f
)
SELECT id,
       name,
       hired_on,
       next_hired_on,
       next_hired_on - hired_on AS days_to_next
FROM paired
ORDER BY hired_on, id;
