## Exercise 5 — runs of a condition

Edit `ex5/solution.sql`.

Works against `orders(id int, customer_id int, status text, total
numeric(10,2), created_at timestamptz)`, restricted to `status = 'paid'` and
`created_at >= '2023-01-01'` — the eleven months January to November 2023,
rolled up to one row per month.

Finance wants the winning streaks: every maximal run of consecutive months
in which `paid` revenue was **higher than the month before**.

This is an islands problem where the thing being run-detected is not a value
in the data but a computed condition. The construction has three steps:
compute the flag with `lag`, keep only the rows where it is true, then apply
the islands trick to *those* months.

Illustration on eight months:

```
   month    | revenue | rising
------------+---------+--------
 2023-01-01 |   100   |          <- no previous month, so not rising
 2023-02-01 |   120   | t
 2023-03-01 |   150   | t
 2023-04-01 |   140   | f
 2023-05-01 |   160   | t
 2023-06-01 |   155   | f
 2023-07-01 |   170   | t
 2023-08-01 |   180   | t

```
 start_month | end_month  | months
-------------+------------+--------
 2023-02-01  | 2023-03-01 |      2
 2023-05-01  | 2023-05-01 |      1
 2023-07-01  | 2023-08-01 |      2

`WHERE rising` keeps only rows that are true.

`month - (row_number() OVER (ORDER BY month) * INTERVAL '1 month')`.

Columns, in this order: `start_month` (a `date`), `end_month` (a `date`),

## Exercise 7 — sessions

Edit `ex7/solution.sql`.

Works against `events(id bigint, customer_id int, event_type text, payload
jsonb, ts timestamptz)` — 3,000,000 rows, one event per second, `ts`
strictly increasing with `id`. Restrict to `customer_id BETWEEN 1 AND 3`,
which gives roughly sixty events per customer spread over five weeks.

Analytics wants those events grouped into **sessions**, where a session ends
whenever more than twelve hours pass with no activity from that customer.
This exercise produces the per-event assignment; the challenge summarises
it.

The row-number trick does not apply — there is no fixed step between
consecutive events. The general construction does:

1. For each event, the gap since that customer's previous event (`lag`).
2. A flag: 1 if this event starts a new session, 0 otherwise. It starts one
   if the gap exceeds twelve hours **or** there is no previous event at all.
3. A running sum of the flag within the customer. That sum is the session
   number, starting at 1.

Illustration for one customer:

```
 id     | ts                     | gap_from_prev | new_session | session_no
--------+------------------------+---------------+-------------+-----------
  10432 | 2023-10-11 04:53:00+00 |               |           1 |          1
  88120 | 2023-10-11 09:12:00+00 | 04:19:00      |           0 |          1
 201933 | 2023-10-12 06:40:00+00 | 21:28:00      |           1 |          2
 244100 | 2023-10-12 07:02:00+00 | 00:22:00      |           0 |          2
```

Without the `IS NULL` half of the flag, the first event of each customer
would score 0 and their sessions would be numbered from 0 while everyone
else's started at 1.

Columns, in this order: `customer_id`, `id`, `ts`, `gap_from_prev` (an
`interval`, NULL for a customer's first event), `session_no` (a running
count starting at 1 within each customer).

**Ordered by `customer_id` ascending, then `ts` ascending.**

```
uv run dojo test v3a05_gaps_and_islands ex7
```

## Hint 1

Two window passes, one after the other. The first looks backwards one row to
decide "is this a new session?". The second turns those yes/no answers into
numbers.

## Hint 2

The second pass is a running total of a flag:

```sql
sum(new_session) OVER (PARTITION BY customer_id ORDER BY ts) AS session_no
```

Every 1 bumps the number; every 0 leaves it alone. That is why the flag has
to be 1 on the *first* row of each customer.

## Hint 3

`ts - lag(ts) OVER w` is an `interval`, and comparing it to `INTERVAL '12
hours'` is a normal comparison — no `extract`, no cast. The decision left to
you is the boundary: is a gap of exactly twelve hours a new session or a
continuation? The prompt says "more than twelve hours", which picks a strict
comparison; say so in the query rather than leaving it to chance.
@@@FILE ex7/importantHints.md
## Hint 1

Start from the flag and reason about the first row. `lag(ts)` is NULL there,
so `ts - NULL` is NULL, so `NULL > INTERVAL '12 hours'` is unknown, so a
plain `CASE WHEN gap > interval THEN 1 ELSE 0 END` falls through to `ELSE`
and produces 0. The running sum then starts at 0 for that customer. Adding
`lag(ts) IS NULL` as an alternative condition is not a nicety; it is what
makes the numbering start at 1.

## Hint 2

Watch the partitioning in both windows. If the `lag` is partitioned but the
`sum` is not, the session numbers keep climbing across customers — customer
2's first session might be number 14. If the `sum` is partitioned but the
`lag` is not, customer 2's first event is compared to customer 1's last and
may not be flagged at all. Both windows need the same `PARTITION BY`, and
writing them with a shared `WINDOW` clause is the cheapest way to guarantee
it.

## Hint 3

A note on cost that is more encouraging than you might expect: both windows
use the same `PARTITION BY customer_id ORDER BY ts`, so PostgreSQL sorts
once and runs two `WindowAgg` nodes over that single ordering. The
"expensive-looking" general construction is one sort, exactly like the
row-number trick. What would cost you a second sort is ordering the two
windows differently — say one by `ts` and the other by `id` — which is easy
to do by accident and produces the same answer for twice the work.
@@@FILE ex7/solution.sql
-- v3a05_gaps_and_islands / ex7 — sessionising events on a 12-hour idle gap.
WITH ev AS (
    SELECT customer_id, id, ts
    FROM events
    WHERE customer_id BETWEEN 1 AND 3
),
flagged AS (
    SELECT customer_id,
           id,
           ts,
           ts - lag(ts) OVER w AS gap_from_prev,
           CASE WHEN lag(ts) OVER w IS NULL
                  OR ts - lag(ts) OVER w > INTERVAL '12 hours'
                THEN 1 ELSE 0 END AS new_session
    FROM ev
    WINDOW w AS (PARTITION BY customer_id ORDER BY ts)
)
SELECT customer_id,
       id,
       ts,
       gap_from_prev,
       sum(new_session) OVER (PARTITION BY customer_id ORDER BY ts) AS session_no
FROM flagged
ORDER BY customer_id, ts;

## Exercise 8 — runs of an unchanged value

Edit `ex8/solution.sql`.

Works against `reviews(id int, product_id int, rating int, body text,
created_at timestamptz)`, restricted to `product_id = 1` — roughly a hundred
reviews, each with a rating from 1 to 5, in time order.

Product quality wants the streaks where the rating did not change: two or
more consecutive reviews (in `created_at, id` order) that all gave the same
score. Runs of a single review are not interesting and must be excluded.

The values here are not consecutive integers, so the difference trick from
exercise 2 does not apply directly. The construction that does is **two**
row numbers:

```
 created_at | rating | rn_all | rn_by_rating | rn_all - rn_by_rating
------------+--------+--------+--------------+----------------------
 t1         |      5 |      1 |            1 |                     0
 t2         |      5 |      2 |            2 |                     0
 t3         |      3 |      3 |            1 |                     2
 t4         |      5 |      4 |            3 |                     1
 t5         |      5 |      5 |            4 |                     1
 t6         |      3 |      6 |            2 |                     4
```

While the rating holds, both counters advance together and their difference
is constant. When the rating changes, only the global counter advances and
the difference moves. The two runs of 5s get keys 0 and 1 — correctly kept
apart — which is why the key alone is not enough: **group by the rating and
the key**, since a 3 and a 5 could produce the same difference on a longer
series.

Given the illustration, the output would be:

```
 rating | run_start | run_end | run_length
--------+-----------+---------+-----------
      5 | t1        | t2      |          2
      5 | t4        | t5      |          2
```

Columns, in this order: `rating`, `run_start` (the `created_at` of the run's
first review), `run_end` (the last), `run_length`. Keep only runs of length
2 or more.

## Spaced review

Edit `review1/solution.sql`.

Works against `staff(id int, name text, department text, manager_id int,
salary numeric(10,2), hired_on date)`, restricted to the 61 people in
`finance`. Hire dates span ten years, so there are long quiet stretches
between hires.

HR wants the three longest hiring droughts: for each consecutive pair of
finance hires (in date order), how long the department went without hiring,
keeping the three longest.

Illustration:

```
 gap_start  | gap_end    | gap_days
------------+------------+----------
 2016-04-11 | 2018-11-30 |      963
 2019-02-02 | 2020-07-15 |      529
 2015-03-02 | 2016-04-11 |      406
```

`gap_start` is the earlier hire's date and `gap_end` the later one, so
`gap_days` is simply `gap_end - gap_start` — two `date` values subtract to
an integer number of days, with no `extract` and no cast.

Two people hired on the same day produce a gap of 0; those rows are
uninteresting but harmless, and they will never reach the top three.

Ties in `gap_days` are broken by the earlier `gap_start`, so the answer is
exactly three rows.

Columns, in this order: `gap_start` (a `date`), `gap_end` (a `date`),
`gap_days` (an integer).

**Ordered by `gap_days` descending, then `gap_start` ascending.** (3 rows.)

## Hint 1

A gap is a property of two adjacent rows, so the first step is to put the
next hire's date onto each row. The rest is subtraction and sorting.

## Hint 2

```sql
lead(hired_on) OVER (ORDER BY hired_on, id) AS next_hired_on
```

The tie-break in the ordering matters when two people share a hire date —
without it, which of them is "next" is undefined.

## Hint 3

The most recent hire has no successor, so `lead` gives NULL and the
subtraction gives NULL. Those rows must not appear in the output. You can
drop them with an explicit `IS NOT NULL` or rely on the ordering — but a
`LIMIT` over a result containing NULLs sorted `DESC` will put them *first*,
because `DESC` defaults to `NULLS FIRST`. That is the decision this exercise
leaves you, and getting it wrong puts an empty row at the top of the report.
@@@FILE review1/importantHints.md
## Hint 1

Predict the trap before you hit it. `ORDER BY gap_days DESC LIMIT 3` on a
column containing a NULL: PostgreSQL's `DESC` puts NULLs first, so your top
three would be one NULL row and two real ones. Either filter the NULL out or
say `NULLS LAST`. Both are correct; only one of them is obvious to the next
reader.

## Hint 2

A second way to get the same answer, worth writing as a cross-check: instead
of `lead`, use a correlated subquery that finds the minimum `hired_on`
strictly after this one. It cannot produce a row for the last hire either,
but it fails differently — the subquery returns NULL rather than the window
returning NULL — and comparing the two is a good way to confirm you
understand what each is doing.

## Hint 3

Notice that this is exercise 1's technique on a different type. There, gaps
were integers between customer ids and you reported the missing values.
Here, gaps are days between hire dates and you report the span. The
mechanism — put the neighbour on the row, subtract, filter — is identical,
which is the point of a spaced review.
@@@FILE review1/solution.sql
-- v3a05_gaps_and_islands / review1 — the three longest finance hiring droughts.
WITH fin AS (
    SELECT hired_on,
           lead(hired_on) OVER (ORDER BY hired_on, id) AS next_hired_on
    FROM staff
    WHERE department = 'finance'
)
SELECT hired_on                  AS gap_start,
       next_hired_on             AS gap_end,
       next_hired_on - hired_on  AS gap_days
FROM fin
WHERE next_hired_on IS NOT NULL
ORDER BY gap_days DESC, gap_start
LIMIT 3;
