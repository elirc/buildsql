# 05 — EF Core basics

Your data has been a static list for five lessons. That was on purpose — it let
routing, DI, middleware and configuration be about themselves. It ends here.
From this lesson on the products live in a real relational database, real SQL
gets generated and executed, and the questions change: not "which element of the
list", but "what query did that turn into, how many round trips did it take, and
did anything actually get written".

If you did the SQL track, you already know the hard half of this. Entity
Framework Core is an **object-relational mapper**: you write LINQ against C#
objects, it translates that into SQL, sends it, and turns the rows back into
objects. Everything you learned about `WHERE`, `ORDER BY`, `JOIN` and indexes is
still true and still your responsibility — the ORM changes who *types* the SQL,
not who is accountable for it.

The database in this lesson is SQLite, held entirely in memory, created fresh
for every single test. That is why an exercise can insert and delete rows
without leaking into the next one.

## Concept — the entity, the context, the query

Three declarations, all in `src/Api/L05_EfcoreBasics/Model.cs`, which is given
code you should read now.

**The entity** is a plain class. No base class, no attributes, no interface:

```csharp
public class Product
{
    public int Id { get; set; }
    public string Name { get; set; } = "";
    public int PriceCents { get; set; }
    public string Category { get; set; } = "";
}
```

EF infers the table name from the `DbSet` property, the column names from the
property names, and — by convention — that a property called `Id` is the
primary key and is generated by the database. Money is an `int` of cents rather
than a `decimal` or a `double` because floating-point money is a bug waiting for
a rounding error.

**The context** is the unit of work:

```csharp
public class CatalogDb(DbContextOptions<CatalogDb> options) : DbContext(options)
{
    public DbSet<Product> Products => Set<Product>();
}
```

A `DbContext` holds an open-ish connection, a change tracker, and one `DbSet`
per table. It is registered with `AddDbContext<CatalogDb>(...)`, which makes it
**scoped** — one instance per HTTP request. That is not a detail: everything a
request loads goes into that one change tracker, and `SaveChangesAsync` writes
all of it in a single transaction. A `DbContext` is emphatically not
thread-safe, and lesson 02's rule about not capturing shorter-lived services
exists largely because of it.

**The query** is LINQ, executed asynchronously:

```csharp
var cheap = await db.Products
    .Where(p => p.PriceCents < 5000)
    .OrderBy(p => p.Name)
    .Select(p => new ProductSummary(p.Id, p.Name, p.PriceCents))
    .ToListAsync();
```

Nothing happens until `ToListAsync()`. Up to that point you are building an
expression tree; the `await` is the moment EF turns it into
`SELECT "p"."Id", "p"."Name", "p"."PriceCents" FROM "Products" AS "p" WHERE …
ORDER BY "p"."Name"` and runs it. This is **deferred execution**, and its most
important consequence is the one in the example: because the `Select` is part of
the expression tree, only three columns are ever fetched. Move the `Select`
after a `.ToList()` and you have loaded every column of every row into memory
first, then thrown most of it away.

Every terminal operator has an async twin — `ToListAsync`, `FirstOrDefaultAsync`,
`SingleAsync`, `CountAsync`, `AnyAsync`, `SaveChangesAsync` — and you should use
them, always. A blocking call to a database inside a request handler holds a
thread pool thread hostage for the whole round trip.

### Writing, and the change tracker

```csharp
db.Products.Add(product);          // nothing has happened yet
await db.SaveChangesAsync();       // INSERT, inside a transaction
```

`SaveChangesAsync` returns the **number of rows written**, which ex4 uses as
evidence. Between loading an entity and saving, EF keeps a snapshot of what it
looked like; on save it compares, generates an `UPDATE` for the differences, and
writes nothing at all if there are none. You never call an `Update` method for
an entity you loaded — assigning to the property is the whole edit.

That only works if the entity is being **tracked**. `AsNoTracking()` tells EF
not to keep the snapshot, which makes read-only queries faster and lighter — and
makes any change you then make to the object invisible to `SaveChangesAsync`.
Silently. That is ex4.

### A word about migrations

In a real project you do not create tables by hand. You change your entity
classes, run `dotnet ef migrations add AddCategory`, and EF generates a C# class
describing the schema delta, which `dotnet ef database update` applies. The
migrations are checked in, run in order, and are the reason a new developer's
database and production's database have the same shape.

This course uses `EnsureCreated()` instead — it builds the schema from the model
in one step, with no history — because a course with a migrations folder would
spend its time on tooling rather than on queries. Know the difference, and know
that `EnsureCreated` is for tests and demos only: it cannot evolve a database
that already exists.

## Exercise 1 — a query and a projection

Edit `src/Api/L05_EfcoreBasics/Ex1.cs`. Implement `ListProducts` so that
`GET /l05/products` answers **200** with every product as a `ProductSummary`,
ordered by name ascending:

```json
[{"id":2,"name":"Bokken","priceCents":5900}, … ]
```

Two things the gate checks. The order — the seeded rows are deliberately not in
name order, and a database makes no promise about the order of an unsorted
`SELECT`. And the shape: `category` must not appear in the response, which means
the `Select` has to be part of the query, not a `.Select(...)` after a
`.ToList()`.

## Exercise 2 — one row, or an honest 404

Edit `src/Api/L05_EfcoreBasics/Ex2.cs`. Implement `GetProduct` so that
`GET /l05/products/{id}` answers **200** with the whole `Product` row — category
included this time — or **404** when there is no such id.

`FirstOrDefaultAsync(p => p.Id == id)` gives you `null` when nothing matches.
Its siblings are worth knowing now: `FirstAsync` throws when there is no match,
`SingleOrDefaultAsync` throws when there is *more than one*, and `FindAsync`
looks in the change tracker before going to the database, which makes it the
fastest way to load by primary key and the only one of the four that is not a
LINQ query.

```
uv run dojo test dotnet 05_efcore_basics ex2
```

## Exercise 3 — Add, Remove, SaveChangesAsync

Edit `src/Api/L05_EfcoreBasics/Ex3.cs`. Two handlers.

`POST /l05/products` takes `{"name":…,"priceCents":…,"category":…}` and answers
**201** with a `Location` header of `/l05/products/{new id}` and the created
product as the body. A blank name or a non-positive `priceCents` is **400**, and
nothing may be written.

`DELETE /l05/products/{id}` answers **204** when the row was there, **404** when
it was not.

The id in that `Location` header is the interesting part: you do not know it
until after `SaveChangesAsync`, because the database generates it. Read
`product.Id` *after* the save and EF will have filled it in for you.

```
uv run dojo test dotnet 05_efcore_basics ex3
```

## Exercise 4 — tracking, proved

Edit `src/Api/L05_EfcoreBasics/Ex4.cs`. Implement
`POST /l05/products/{id}/rename?name=…&tracked=true|false` so that it loads the
product — **with tracking when `tracked` is true, with `AsNoTracking()` when it
is false** — assigns the new name, saves, and answers **200** with:

```json
{"changes": <what SaveChangesAsync returned>, "name": <the name on your object>}
```

…or **404** when there is no such product.

Run it both ways and look at what comes back. Tracked: `changes` is 1 and the
row really changes. Untracked: `name` is the new name — the assignment
obviously worked — `changes` is **0**, and the database is untouched. No
exception, no warning, nothing in the log. This is the single most expensive
beginner mistake with EF Core, and the point of making you produce it on purpose
is that you will recognise it in the wild.

```
uv run dojo test dotnet 05_efcore_basics ex4
```

## Challenge — a page and its total

Honest difficulty note: the query is four operators; the validation and the
1-based arithmetic are where the bugs are.

Edit `src/Api/L05_EfcoreBasics/Challenge.cs`. Implement
`GET /l05/products/page?page=&size=` returning:

```json
{"items":[…],"total":5,"page":2,"size":2}
```

`items` is one page of `ProductSummary`, name ascending. `total` is the number
of rows in the table, not the number you returned — that is what lets a client
render page numbers. `page` defaults to 1 and `size` to 2, both are echoed back,
and **page < 1, size < 1 or size > 50 is a 400**.

That upper bound is not busywork. An endpoint that will happily accept
`?size=1000000` is a denial-of-service vector that any client can trigger by
accident.

```
uv run dojo test dotnet 05_efcore_basics challenge
```

## The gate

This is the entire gate class, `tests/Gates/L05_EfcoreBasicsTests.cs`:

```csharp
using System.Net;
using System.Net.Http.Json;
using DotnetDojo.Api.L05_EfcoreBasics;
using Microsoft.EntityFrameworkCore;

namespace DotnetDojo.Gates;

public class L05_EfcoreBasicsTests
{
    [Fact]
    public async Task Ex1_ListingProductsProjectsAndSorts()
    {
        using var host = NewHost();
        using var client = host.CreateClient();

        var response = await client.GetAsync("/l05/products");
        await Teach.Status(HttpStatusCode.OK, response,
            "GET /l05/products must answer 200 - reread README ex1.");

        Teach.Equal("2,4,5,1,3", await Ids(response),
            "Every product, name ascending: Bokken, Gi, Obi, Tatami mat, Zabuton. Getting "
                + "1,2,3,4,5 means you never ordered - the order rows come back in is not a "
                + "promise the database makes.");

        string raw = await client.GetStringAsync("/l05/products");
        Teach.True(!raw.Contains("category", StringComparison.OrdinalIgnoreCase),
            "The list is meant to be a ProductSummary - id, name and price only. \"category\" "
                + "in the body means you returned whole Product entities, which sends columns "
                + "nobody asked for over the wire. Project with Select before ToListAsync.\n"
                + "  body: " + raw);
    }

    [Fact]
    public async Task Ex2_OneProductOrA404()
    {
        using var host = NewHost();
        using var client = host.CreateClient();

        var found = await client.GetAsync("/l05/products/4");
        await Teach.Status(HttpStatusCode.OK, found,
            "GET /l05/products/4 must answer 200 - reread README ex2.");

        var product = await found.Content.ReadFromJsonAsync<ProductDto>();
        Teach.Equal("Gi", product?.Name,
            "Product 4 is the Gi. If you always get \"Tatami mat\", the id is not reaching the "
                + "query.");
        Teach.Equal("clothing", product?.Category,
            "This endpoint returns the whole row, category included - unlike the list in ex1.");

        var missing = await client.GetAsync("/l05/products/99");
        await Teach.Status(HttpStatusCode.NotFound, missing,
            "There is no product 99. FirstOrDefaultAsync gives you null for that; First "
                + "would throw, and a thrown exception is a 500.");
    }

    [Fact]
    public async Task Ex3_CreateAndDeleteReallyChangeTheDatabase()
    {
        using var host = NewHost();
        using var client = host.CreateClient();

        var created = await client.PostAsJsonAsync("/l05/products",
            new { name = "Shinai", priceCents = 4500, category = "training" });
        await Teach.Status(HttpStatusCode.Created, created,
            "A successful POST is 201 Created - reread README ex3.");
        Teach.Equal("/l05/products/6", created.Headers.Location?.ToString(),
            "The Location header points at the new row. Five products are seeded, so the "
                + "database gives the new one id 6 - and you only know that after "
                + "SaveChangesAsync, because the id is generated by the database.");

        var fetched = await client.GetAsync("/l05/products/6");
        await Teach.Status(HttpStatusCode.OK, fetched,
            "The new product has to still be there on the next request. A 404 means you "
                + "called Add but never SaveChangesAsync - nothing left the change tracker.");
        Teach.Equal(6, host.Query(db => db.Products.Count()),
            "The table should hold six rows now.");

        var blank = await client.PostAsJsonAsync("/l05/products",
            new { name = "  ", priceCents = 4500, category = "training" });
        await Teach.Status(HttpStatusCode.BadRequest, blank,
            "A blank name is a 400, and nothing should be written.");

        var free = await client.PostAsJsonAsync("/l05/products",
            new { name = "Freebie", priceCents = 0, category = "training" });
        await Teach.Status(HttpStatusCode.BadRequest, free,
            "priceCents has to be positive.");
        Teach.Equal(6, host.Query(db => db.Products.Count()),
            "Two rejected requests must not have inserted anything. Validate before Add.");

        var deleted = await client.DeleteAsync("/l05/products/5");
        await Teach.Status(HttpStatusCode.NoContent, deleted,
            "A successful DELETE has nothing to say: 204.");
        Teach.Equal(5, host.Query(db => db.Products.Count()),
            "The row should be gone from the table, not just from the response.");

        var gone = await client.GetAsync("/l05/products/5");
        await Teach.Status(HttpStatusCode.NotFound, gone, "…so fetching it is now a 404.");

        var again = await client.DeleteAsync("/l05/products/5");
        await Teach.Status(HttpStatusCode.NotFound, again,
            "Deleting something that is not there is a 404: you cannot remove an entity you "
                + "did not load.");
    }

    [Fact]
    public async Task Ex4_TrackingIsWhatMakesASaveWorkAtAll()
    {
        using var host = NewHost();
        using var client = host.CreateClient();

        var untracked = await client.PostAsync("/l05/products/3/rename?name=Cushion&tracked=false", null);
        await Teach.Status(HttpStatusCode.OK, untracked,
            "POST /l05/products/3/rename?name=Cushion&tracked=false must answer 200 - "
                + "reread README ex4.");

        var untrackedBody = await untracked.Content.ReadFromJsonAsync<RenameDto>();
        Teach.Equal("Cushion", untrackedBody?.Name,
            "The object in memory really was renamed - assigning to a property always works.");
        Teach.Equal(0, untrackedBody?.Changes,
            "SaveChangesAsync returned something other than 0 for an AsNoTracking query. "
                + "An untracked entity is not in the change tracker, so EF has no idea it "
                + "changed and writes nothing.");
        Teach.Equal("Zabuton", host.Query(db => db.Products.Single(p => p.Id == 3).Name),
            "…and the database still says Zabuton. This is the AsNoTracking trap: no "
                + "exception, no warning, no update.");

        var tracked = await client.PostAsync("/l05/products/2/rename?name=Shinai&tracked=true", null);
        var trackedBody = await tracked.Content.ReadFromJsonAsync<RenameDto>();
        Teach.Equal(1, trackedBody?.Changes,
            "A tracked entity that you changed produces exactly one write, and "
                + "SaveChangesAsync returns the number of rows it touched. You do not call "
                + "Update - the change tracker already noticed.");
        Teach.Equal("Shinai", host.Query(db => db.Products.Single(p => p.Id == 2).Name),
            "…and this time the row really changed.");

        var missing = await client.PostAsync("/l05/products/99/rename?name=Nope&tracked=true", null);
        await Teach.Status(HttpStatusCode.NotFound, missing,
            "Renaming a product that does not exist is a 404.");
    }

    [Fact]
    public async Task Challenge_APageAndItsTotal()
    {
        using var host = NewHost();
        using var client = host.CreateClient();

        var second = await client.GetAsync("/l05/products/page?page=2&size=2");
        await Teach.Status(HttpStatusCode.OK, second,
            "GET /l05/products/page?page=2&size=2 must answer 200 - reread README challenge.");

        var page = await second.Content.ReadFromJsonAsync<PageDto>();
        Teach.Equal("5,1", string.Join(",", (page?.Items ?? []).Select(i => i.Id)),
            "By name the order is Bokken, Gi, Obi, Tatami mat, Zabuton; page 2 of size 2 is "
                + "the third and fourth of those - Obi and Tatami mat. Skip before Take, and "
                + "order before both.");
        Teach.Equal(5, page?.Total,
            "total is how many rows exist, not how many you returned - that is what lets a "
                + "client draw the page numbers.");
        Teach.Equal(2, page?.Page, "Echo back the page you served.");
        Teach.Equal(2, page?.Size, "…and the size.");

        var defaults = await client.GetFromJsonAsync<PageDto>("/l05/products/page");
        Teach.Equal("2,4", string.Join(",", (defaults?.Items ?? []).Select(i => i.Id)),
            "With no query string at all, page defaults to 1 and size to 2.");

        var zero = await client.GetAsync("/l05/products/page?page=0");
        await Teach.Status(HttpStatusCode.BadRequest, zero,
            "Pages are 1-based, so page=0 is a 400.");

        var huge = await client.GetAsync("/l05/products/page?size=51");
        await Teach.Status(HttpStatusCode.BadRequest, huge,
            "An unbounded page size is how one client takes the database down. Cap it at 50 "
                + "and reject anything larger.");
    }

    [Fact]
    public async Task Review1_TheCheapestFew()
    {
        using var host = NewHost();
        using var client = host.CreateClient();

        var response = await client.GetAsync("/l05/review/products/cheapest");
        await Teach.Status(HttpStatusCode.OK, response,
            "GET /l05/review/products/cheapest must answer 200 - reread README review.");
        Teach.Equal("5,3,2", await Ids(response),
            "Cheapest three: Obi 2400, Zabuton 3400, Bokken 5900. The default limit is 3.");

        var one = await client.GetAsync("/l05/review/products/cheapest?limit=1");
        Teach.Equal("5", await Ids(one), "limit=1 gives just the cheapest.");

        var zero = await client.GetAsync("/l05/review/products/cheapest?limit=0");
        await Teach.Status(HttpStatusCode.BadRequest, zero,
            "Asking for zero rows is a malformed request, not an empty list: 400.");
    }

    private static SqliteHost<CatalogDb> NewHost() =>
        new SqliteHost<CatalogDb>().Seed(db => db.Products.AddRange(
            new Product { Id = 1, Name = "Tatami mat", PriceCents = 12500, Category = "equipment" },
            new Product { Id = 2, Name = "Bokken", PriceCents = 5900, Category = "training" },
            new Product { Id = 3, Name = "Zabuton", PriceCents = 3400, Category = "equipment" },
            new Product { Id = 4, Name = "Gi", PriceCents = 8900, Category = "clothing" },
            new Product { Id = 5, Name = "Obi", PriceCents = 2400, Category = "clothing" }));

    private static async Task<string> Ids(HttpResponseMessage response)
    {
        var items = await response.Content.ReadFromJsonAsync<List<SummaryDto>>();
        return string.Join(",", (items ?? []).Select(i => i.Id));
    }

    private sealed record SummaryDto(int Id, string? Name, int PriceCents);

    private sealed record ProductDto(int Id, string? Name, int PriceCents, string? Category);

    private sealed record RenameDto(int Changes, string? Name);

    private sealed record PageDto(List<SummaryDto>? Items, int Total, int Page, int Size);
}
```

In plain English: notice what is different about this gate. There is no
`IClassFixture` — every test calls `NewHost()`, which opens its own private
in-memory SQLite database and seeds the same five products, so ex3 can delete a
row without ex4 ever knowing. And several assertions use `host.Query(...)` to
read the database *directly*, outside any request: an endpoint that answers 204
but never wrote anything would pass an HTTP-only check and fails here.

## The teaching point

The one habit worth building: **know what SQL your LINQ became.** Not
approximately — actually. In a real project you turn on
`optionsBuilder.LogTo(Console.WriteLine)` in development and read the generated
statements while you work, the same way you would read an `EXPLAIN` in the SQL
course. Every serious performance problem in an EF codebase is visible in that
log long before it is visible in a dashboard.

The second is that the ORM will not save you from the database. Ordering, paging
limits, indexes, transaction boundaries and round-trip counts are still yours.
What EF buys you is that the mapping code and the parameterised SQL are written
correctly and consistently, which is a real and large saving — and a very
different claim from "you no longer have to think about the database".
